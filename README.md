# LINE personal tracker

Webhook LINE OA สำหรับบันทึกรายรับ รายจ่าย อาหาร การออกกำลังกาย และน้ำหนักด้วยข้อความภาษาไทย ใช้ Node.js 22+, OpenAI SDK, MySQL 8+ และ deploy บน Vercel ได้

## เริ่มใช้งาน

โปรเจกต์มี `.env` อยู่แล้ว ให้เติมค่าที่ว่าง หากเริ่มจาก checkout ใหม่ให้คัดลอก `.env.example` เป็น `.env` ก่อน

```powershell
npm.cmd ci
npm.cmd start
```

บน macOS/Linux ใช้ `npm` แทน `npm.cmd` ได้ บน Windows ใช้ `npm.cmd` ได้แม้ PowerShell ปิดการรัน script

ค่าที่ต้องใส่:

| Env | ค่า |
| --- | --- |
| `LINE_CHANNEL_SECRET` | Channel secret จาก LINE Developers |
| `LINE_CHANNEL_ACCESS_TOKEN` | Messaging API channel access token |
| `OPENAI_API_KEY` | API key ของผู้ให้บริการ |
| `OPENAI_BASE_URL` | URL ราก API เช่น `https://api.openai.com/v1` ไม่ต่อท้าย `/responses` |
| `OPENAI_MODEL` | ชื่อโมเดลที่ endpoint รองรับ ค่าเริ่มต้น `gpt-4.1-mini` |
| `OPENAI_API_MODE` | `responses` สำหรับ OpenAI หรือ `chat` สำหรับบริการที่รองรับ Chat Completions |
| `MYSQL_HOST`, `MYSQL_PORT` | ที่อยู่ MySQL ค่า port เริ่มต้น 3306 |
| `MYSQL_USER`, `MYSQL_PASSWORD` | บัญชี MySQL |
| `MYSQL_DATABASE` | ชื่อ database ใช้ตัวอักษร ตัวเลข หรือ `_` |
| `MYSQL_SSL` | `true` สำหรับฐานข้อมูล cloud ที่ใช้ TLS |
| `MYSQL_SSL_CA` | CA certificate ถ้าผู้ให้บริการกำหนด รองรับ literal `\n` |
| `MYSQL_CREATE_DATABASE` | `true` สร้าง database อัตโนมัติ; `false` เมื่อผู้ให้บริการสร้างไว้แล้วและไม่ให้สิทธิ์ CREATE DATABASE |
| `APP_TIMEZONE` | ค่าเริ่มต้น `Asia/Bangkok` |
| `PORT` | port สำหรับรัน local ค่าเริ่มต้น 3000 |

บริการ custom URL และโมเดลต้องรองรับ structured outputs แบบ JSON schema ใน API mode ที่เลือก ไม่ใช่ทุกบริการที่ใช้รูปแบบ OpenAI จะรองรับทั้งหมด ไม่มี fallback ที่ข้าม validation

เมื่อ `npm.cmd start` จะสร้าง database และตารางที่ขาดก่อนเปิด server บัญชี MySQL ต้องมีสิทธิ์สร้าง database/table และอ่าน/เขียนข้อมูล การตั้ง `MYSQL_CREATE_DATABASE=false` ข้ามเฉพาะการสร้าง database; ยังคงสร้างตารางอัตโนมัติ

ตรวจได้ที่ `GET /health` (server ทำงาน) และ `GET /ready` (เชื่อมต่อฐานข้อมูลและสร้างตารางสำเร็จ) หรือสั่ง `npm.cmd run db:init` เพื่อเตรียม schema

## ตัวอย่างข้อความ

พิมพ์ `ช่วยทำอะไรได้บ้าง`, `มีฟังก์ชั่นอะไรบ้าง` หรือถามวิธีใช้บอต ระบบจะแสดงฟังก์ชันที่รองรับทั้งหมดพร้อมตัวอย่างเป็นข้อความธรรมดาสำหรับ LINE คำตอบใช้รายการฟังก์ชันจากแอปโดยตรง และไม่ยกเลิกข้อความที่กำลังรอข้อมูลเพิ่ม

| ข้อความ | ผล |
| --- | --- |
| `รับเงินเดือน 30000 บาท` | รายรับ หมวดเงินเดือน |
| `จ่ายค่ากาแฟ 60 บาท` | รายจ่าย หมวดอาหาร ไม่บันทึกว่ากิน |
| `กินข้าวผัด` | อาหาร 1 หน่วย รายละเอียดเป็น null |
| `กินส้มตำ 2 จาน ไม่เผ็ด` | เมนูส้มตำ จำนวน 2 จาน รายละเอียดไม่เผ็ด |
| `วิ่ง 30 นาที` | ออกกำลัง 30 นาที ประเมินแคลเมื่อมีน้ำหนักและข้อมูลกิจกรรมเพียงพอ |
| `วิ่ง 1 ชั่วโมง 300 แคล` | ออกกำลัง 60 นาที 300 แคล |

| `เมื่อวานจ่ายค่าแท็กซี่ 120 บาท` | รายจ่ายย้อนหลังในเวลาท้องถิ่น |
| `รายจ่ายเดือนนี้รวมเท่าไร` | สรุปจากข้อมูลของผู้ส่งเท่านั้น |
| `สรุปวันนี้` หรือ `สรุปเดือนนี้` | ภาพรวมทุกประเภทในช่วงที่ระบุ พร้อมคำแนะนำและน้ำหนักล่าสุด |
| `วันนี้กินอะไรบ้าง` | ดูรายการอาหาร |
| `น้ำหนักล่าสุดเท่าไร` | น้ำหนักล่าสุด |
| `ลบรายจ่ายล่าสุด 3 แถว` | ลบเฉพาะ expense ของผู้ส่ง เรียงตามรายการที่เพิ่งบันทึก |
| `ลบอาหารล่าสุด 2 แถว` | ลบ food ของผู้ส่ง และตอบจำนวนที่ลบจริงพร้อมชื่อตาราง |
| `จ่ายค่ากาแฟ` แล้ว `60 บาท` | ถามจำนวนเงินก่อน แล้วบันทึกหลังได้ข้อมูลครบ |
| `ยกเลิก` | ยกเลิกข้อความที่รอข้อมูลเพิ่ม โดยไม่ลบข้อมูลที่บันทึกแล้ว |

รองรับหลายรายการในข้อความเดียว หากข้อมูลจำเป็นบางรายการขาด จะถามก่อนและยังไม่บันทึกทั้งข้อความ การถามข้อมูลพร้อมสั่งบันทึกหรือลบในข้อความเดียวจะขอให้แยกคำสั่ง

บอตชื่อ Wella เป็นผู้ช่วยผู้หญิงด้านการเงินและสุขภาพ น้ำเสียงอารมณ์ดี อ่อนโยน ไพเราะ คุยภาษาไทยเป็นธรรมชาติและกระชับ ทุกคำตอบใช้คำลงท้ายสุภาพแบบผู้หญิง โดยใช้ “คะ” กับคำถามหรือ “นะคะ” และ “ค่ะ” กับประโยคบอกเล่า ตอบหลังบันทึกสำเร็จว่า `บันทึกเรียบร้อยค่ะ` หรือแจ้งจำนวนรายการ ถ้าอ่านข้อมูลจะตอบตามผลจากฐานข้อมูล ถ้าข้อมูลขาดจะถามเฉพาะส่วนที่จำเป็น ไม่ตัดสินการใช้เงิน อาหาร หรือน้ำหนัก และไม่แทรกคำแนะนำโดยไม่ได้ถาม หากระบบขัดข้องจะไม่อ้างว่าบันทึกสำเร็จ System prompts ทั้งหมดเป็นภาษาอังกฤษ

## ผู้ช่วยการเงินและเทรนเนอร์สุขภาพ

หลังบันทึกการเงินทุกครั้งจะแจ้งยอดรายจ่ายวันนี้จากฐานข้อมูล หลังบันทึกการกินทุกครั้งจะแจ้งยอดแคลอาหารวันนี้จากฐานข้อมูล วันที่อิงเวลา LINE event ตาม `APP_TIMEZONE`; รายการย้อนหลังนับในวันที่กิน/ใช้จ่ายจริง ไม่ย้ายไปวันปัจจุบัน ยอด “วันนี้” จึงอาจไม่เพิ่มเมื่อบันทึกย้อนหลัง

อาหารที่ไม่ได้แจ้งแคลจะประเมินผ่าน LLM แยกจากขั้นตอนอ่านข้อมูล โดยคำนึงถึงเมนู จำนวน หน่วย และรายละเอียด ถ้าเป็นหน่วยทั่วไปจะระบุสมมติฐานขนาดอาหารไว้ ไม่แก้หน่วยหรือรายละเอียดต้นฉบับ การออกกำลังที่ไม่แจ้งแคลจะใช้กิจกรรม ระยะเวลา และน้ำหนักที่บันทึกเพื่อประเมินเมื่อข้อมูลเพียงพอ ค่าแคลเป็นยอดรวมต่อรายการ ถ้าผู้ใช้แจ้งยอดมาแล้วจะไม่ประเมินซ้ำ

ค่าประเมินบันทึกใน `calories` พร้อม `calories_source=estimated` และ `calorie_note` ส่วนค่าที่ผู้ใช้ระบุเก็บ `calories_source=provided` ยอดที่มีค่าประเมินจะแสดงว่า “ประมาณ” ถ้ายังประเมินไม่ได้จะเก็บ null และแจ้งว่ายอดแคลยังไม่ครบ ไม่ใส่ 0 แทนค่าที่ไม่ทราบ หาก API ประเมินล้มเหลว ยังบันทึกข้อมูลที่ผู้ใช้แจ้งได้ แคลอาหารกับแคลออกกำลังแสดงแยกกัน ไม่ใช้ผลต่างเป็นการประเมินภาวะขาดแคล

เมื่อพิมพ์ `สรุป`, `สรุปวันนี้`, `สรุปเมื่อวาน` หรือระบุช่วงวัน จะใช้ intent `overview` สรุปยอดจากทุกรายการทุกประเภทในช่วงนั้น ไม่จำกัดแค่รายการตัวอย่าง พร้อมดูน้ำหนักล่าสุดนอกช่วงประกอบโดยระบุวันที่ชัดเจน หากไม่บอกช่วงจะใช้วันนี้ การถามยอดเฉพาะ เช่น `วันนี้ใช้ไปเท่าไร` ยังใช้ query ตามประเภท

ถ้าน้ำหนักล่าสุดเก่าตั้งแต่ 7 วันขึ้นไป จะชวนอัปเดตเพื่อดูความคืบหน้า เกณฑ์ 7 วันนี้เป็นค่าของฟีเจอร์เตือนในแอป ไม่ใช่เกณฑ์วินิจฉัย และไม่มีการสรุปว่าไม่ก้าวหน้าจากการขาดข้อมูลน้ำหนัก

เมื่อต้องการคำแนะนำ พิมพ์ เช่น `แนะนำด้านการเงินหน่อย`, `แนะนำด้านสุขภาพหน่อย`, `แนะนำเรื่องการกินหน่อย`, `ควรออกกำลังยังไงต่อ` หรือ `ดูน้ำหนักแล้วแนะนำหน่อย` ระบบจะแยกเป็น intent `advice` และดึงข้อมูลของ LINE user นั้นจากฐานข้อมูลก่อนส่งให้ LLM แนะนำ ไม่ใช้คำตอบทั่วไปแทนการดูประวัติ

การเงินใช้รายรับ รายจ่าย และหมวดของเดือนปัจจุบันจนถึงวันที่ถาม โดยยอดรวมครอบคลุมทุกรายการที่ตรงช่วงเวลา ส่วนรายการตัวอย่างแสดงล่าสุดไม่เกิน 10 รายการต่อประเภท สุขภาพใช้อาหารและการออกกำลัง 30 วันจนถึงวันที่ถาม และน้ำหนักล่าสุดไม่เกิน 10 ครั้ง พร้อมเปรียบเทียบกับครั้งก่อนหน้าคนละวันที่ ถ้ามีข้อมูลไม่พอจะไม่แต่งแนวโน้มขึ้นมา

คำตอบเน้นใจความสำคัญ ใช้จุดนำหน้า • ทีละประเด็น แยกหัวข้อด้วยบรรทัดว่าง และปิดท้ายด้วยสรุปสั้น ๆ โดยทั่วไปประมาณ 300–600 ตัวอักษร ยกเว้นเมื่อขอรายละเอียดหรือรายการทั้งหมด การยืนยันสั้น ๆ ไม่ต้องมี bullet ข้อเสนอไม่ถูกบันทึกเป็นเหตุการณ์จริง คำตอบ LINE ใช้ plain text ไม่มี Markdown และมีตัวแปลงข้อความก่อนส่งเพื่อเอารูปแบบ Markdown ทั่วไปออก โดยเก็บจุดนำหน้า • ไว้

ถ้ายังไม่มีข้อมูลจะบอกตามตรง พร้อมแนะนำจุดเริ่มต้นทั่วไปและถามข้อมูลที่จำเป็น การไม่มีบันทึกไม่ได้แปลว่าไม่กินหรือไม่ออกกำลัง ไม่ประเมินว่าอ้วนหรือต้องลดน้ำหนักจากน้ำหนักอย่างเดียว และจะถามเป้าหมาย ส่วนสูง อายุ และข้อจำกัดที่เกี่ยวข้องก่อนแนะนำเป้าหมายเฉพาะบุคคล การดูแนวโน้มไม่ใช่การวินิจฉัยสุขภาพ

แนะนำเมื่อผู้ใช้ขอคำแนะนำหรือขอสรุปภาพรวม ไม่ส่งข้อความเตือนตามเวลา ข้อความบันทึกการเงินและอาหารจะแสดงยอดรายวัน ส่วนบันทึกประเภทอื่นยังตอบสั้น ๆ System prompts ทั้งหมดเป็นภาษาอังกฤษ แนวทางทั่วไปด้านสุขภาพอ้างอิง [WHO healthy diet](https://www.who.int/news-room/fact-sheets/detail/healthy-diet) และ [WHO physical activity](https://www.who.int/news-room/fact-sheets/detail/physical-activity) การประเมินแคลใช้ LLM พร้อมสมมติฐาน ไม่ได้เรียกฐานข้อมูลอาหารที่ตรวจวัดจริง

## ฐานข้อมูล 3 ตาราง

`entries` รวมข้อมูลทั้ง 5 ประเภทในตารางเดียว แยกด้วย `type`: `income`, `expense`, `food`, `exercise`, `weight` มี `line_user_id`, ชื่อรายการ, รายละเอียด, จำนวนเงิน, หมวด, จำนวนอาหาร/หน่วย, เวลาออกกำลัง, แคล, น้ำหนัก และ `occurred_at`

วันที่ เวลา ปี เดือน เลขวันที่ และชื่อวันภาษาไทย (`จันทร์`, `อังคาร`, `พุธ` ฯลฯ) สร้างเป็น generated columns จาก `occurred_at` อัตโนมัติ จึงตรงกันเสมอ รายละเอียดอาหารที่ไม่ได้แจ้งเก็บ null ส่วนแคลที่ไม่ได้แจ้งจะประเมินเมื่อข้อมูลเพียงพอและแยกที่มาไว้ ถ้าไม่พอเก็บ null

เมื่อเริ่มแอปจะเพิ่มคอลัมน์ `calories_source` และ `calorie_note` ให้ตารางเดิมอัตโนมัติ ต้องมีสิทธิ์ ALTER TABLE ค่าที่มีอยู่จากเวอร์ชันเดิมจะระบุเป็น provided โดยไม่เปลี่ยนค่าแคล ไม่มีการประเมินย้อนหลังให้รายการเก่าโดยอัตโนมัติ

อีกสองตารางเป็นสถานะระบบ: `user_state` เก็บข้อความที่รอคำตอบไม่เกิน 30 นาที และ `webhook_events` กันการบันทึกซ้ำเมื่อ LINE ส่ง webhook เดิมอีกครั้ง ทั้งสองมี LINE user ID และเวลาของสถานะ/เหตุการณ์ ไม่มีตารางแยกสำหรับแต่ละประเภท

ทุกการค้นและลบใช้ user ID จาก LINE event ที่ตรวจลายเซ็นแล้ว ไม่รับ user ID หรือ SQL จาก LLM ใช้ parameterized queries และ transaction พร้อม lock ต่อ user ข้อมูลส่วนตัวรองรับเฉพาะแชท 1:1 ไม่ตอบข้อมูลใน group/room

Validation ตรวจ schema ชื่อ/รายละเอียดที่ต้องตรงข้อความต้นฉบับ หลักฐานตัวเลข และฟิลด์ที่ใช้กับแต่ละประเภท การตีความเจตนาและวันสัมพัทธ์ยังอาศัย LLM จึงควรทดสอบกับโมเดลจริงที่เลือกก่อนใช้งาน

## Deploy Vercel

1. นำโฟลเดอร์นี้ขึ้น repository แล้ว import เข้า Vercel หรือรัน `npx vercel` จากโฟลเดอร์นี้
2. ตั้ง Node.js 22 หรือสูงกว่า ตั้ง Framework เป็น Other และไม่ต้องใส่ build command; API routes อยู่ใน `api/` และ rewrites อยู่ใน `vercel.json`
3. ใส่ environment variables ของ LINE, OpenAI และ MySQL ใน Vercel Project Settings; `.env` ไม่ถูกอัปโหลดเป็นค่าของ production โดยอัตโนมัติ
4. ใช้ฐานข้อมูล MySQL ที่ Vercel เชื่อมต่อผ่านเครือข่ายได้ เปิด TLS ตามผู้ให้บริการ และ deploy
5. เปิด `https://YOUR-DOMAIN/ready` หนึ่งครั้งเพื่อตรวจ/เตรียม schema (serverless เริ่ม init ตอนเรียกใช้ฐานข้อมูลครั้งแรก)
6. ใน LINE Developers ตั้ง Webhook URL เป็น `https://YOUR-DOMAIN/webhook` กด Verify เปิด Use webhook และ Webhook redelivery ปิดข้อความตอบกลับอัตโนมัติที่อาจตอบซ้ำ

สำหรับ local ใช้ HTTPS tunnel ไปที่ port 3000 แล้วตั้ง URL `/webhook` ที่ LINE

Webhook ตรวจ HMAC จาก raw body ก่อน parse JSON และ commit ข้อมูลก่อนตอบ LINE ถ้า reply ล้มเหลว webhook เดิมจะใช้ผลที่บันทึกไว้โดยไม่บันทึกซ้ำ บอตใช้ reply token ของ LINE จึงควรเลือกโมเดลที่ตอบเร็ว; ไม่ใช้ push message ทดแทนอัตโนมัติ

การ deploy นี้เตรียมสำหรับ Vercel ยังไม่ได้สร้าง Cloudflare Worker เพราะต้องมีการตั้งค่าการเชื่อมต่อ MySQL แยกสำหรับ runtime นั้น

## ทดสอบ

```powershell
npm.cmd test
npm.cmd run check
npm.cmd run test:db
npm.cmd run test:llm
npm.cmd run test:features
```

- `test`: ไม่ต้องใส่ key ทดสอบลายเซ็น webhook, raw body บน adapter ของ Vercel, การแยก user, validation, defaults, clarification, การกันซ้ำ และ OpenAI SDK ทั้งสอง mode กับ HTTP server จำลอง
- `check`: ตรวจ syntax ของ source, API, scripts และ tests
- `test:db`: ใช้การเชื่อมต่อ MySQL จาก `.env` สร้าง database ทดสอบชื่อสุ่มใหม่ และลบเฉพาะ database นี้หลังทดสอบ ต้องมีสิทธิ์ CREATE/DROP DATABASE ไม่แก้ข้อมูล app
- `test:llm`: ต้องใส่ env ที่ครบ เรียกโมเดลจริงตรวจข้อความตัวอย่าง มีค่า API ตามผู้ให้บริการ ไม่เขียนข้อมูลลง MySQL
- `test:features`: เรียกโมเดลจริงทดสอบการแยกอาหาร/ออกกำลัง การประเมินแคล และสรุปภาพรวมพร้อมเตือนน้ำหนักเก่า ใช้ข้อมูลจำลอง ไม่เขียน MySQL หรือส่งข้อความ LINE มีค่า API ตามผู้ให้บริการ
